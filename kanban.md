- [ ] **🟡 US-CLONE-PROGRESS — Progresso granular (%/objetos) da clonagem de Project em tempo real** *(derivado da exploração 2026-08-13: hoje a UI só mostra o estado coarse `pending→cloning→ready|failed` via WS `project.clone_state`; durante `cloning` o badge fica estático, sem % nem contagem de objetos — igual ao que o `git clone` mostra no terminal)*
  - **Sintoma:** ao clonar um repo grande, o usuário vê o badge "clonando" parado e não sabe se travou ou quanto falta. O `git clone` de terminal mostra `Receiving objects: 42% (420/1000), 1.2 MiB | 800 KiB/s` — queremos paridade disso na UI.
  - **Estado-atual verificado (código):** `ProjectWorkspaceService.doClone` (apps/api/src/modules/projects/project-workspace.service.ts) chama `git.clone` (isomorphic-git) **SEM `onProgress`** no modo https, e `systemGitClone` usa `execFileAsync('git', ['clone', ...])` **sem `--progress`/parse de stderr** no modo ssh. Não há dado de byte/percent/fase em lugar nenhum — só as 3 transições do enum `ProjectCloneState`. O evento WS `ProjectCloneStateEvent` (packages/shared/src/events.ts) carrega `{projectId, state, error?}`. `RealtimeService.broadcast` (fan-out real) já funciona; `useRealtime.ts:158` já reage invalidando React Query.
  - **Escopo proposto (PR-a-PR):**
    1. **Backend https (isomorphic-git):** passar `onProgress: (p) => ...` ao `git.clone` — `p` traz `{phase, loaded, total}`. Throttle (~250–500ms ou por Δ%) para não floodar o WS.
    2. **Backend ssh (systemGit):** adicionar `--progress` ao `git clone`, trocar `execFileAsync` por `spawn` e parsear o **stderr** linha a linha (regex das fases `Counting/Compressing/Receiving/Resolving objects`) → mesmo shape `{phase, loaded, total}`.
    3. **Contrato compartilhado:** novo evento WS `ProjectCloneProgressEvent` (`type:'project.clone_progress'`, `{projectId, phase, loaded, total, percent}`) em packages/shared/src/events.ts + união `ServerEvent` (atualizar api **e** web — invariante type-safe). NÃO sobrecarregar `ProjectCloneStateEvent` (semânticas distintas: transição discreta vs progresso contínuo).
    4. **Frontend:** `useRealtime.ts` guarda o progresso mais recente por `projectId` (state leve, sem invalidar React Query a cada tick — só o `clone_state` final invalida). `CloneStateBadge` (ProjectsManager.tsx + ProjectExplorer.tsx) mostra barra/percent + fase enquanto `state==='cloning'`; ao chegar `ready`/`failed`, volta ao badge normal.
  - **Invariantes/cuidados:** progresso é **efêmero** (não persistir em `Project` — só WS transiente); throttle obrigatório; se `total` for desconhecido (fase Counting), mostrar spinner indeterminado; não vazar credencial em nenhuma linha de stderr logada. `git.clone` do isomorphic-git só reporta progresso das fases que ele executa (download); para repos ssh a fidelidade vem do `git` do sistema.
  - **DOD:** durante o clone (https **e** ssh) a UI mostra %/fase/objetos atualizando em tempo real via WS; ao concluir, badge vira `pronto`; ao falhar, `falhou` + `lastError`; progresso não é persistido; contrato type-safe nos 2 lados; build+lint+test verdes.

- [ ] **🔴 BUG-BRIDGE1 — O bridge do Copilot DESCARTA `evidence` e `learnings`; e prosa com exit 0 fecha task como `done:true`** *(descoberto pelo oráculo da US-F3.2, 2026-08-29 — pré-existente)*
  - **Verificado pelo orquestrador em `docker/copilot-cli-adapter.mjs:355-362`:** o `result` emitido monta `summary`/`dodTouched`/`proposedDod`/`affectedFlows`/`nextStep`/`done`. Os campos `evidence` e `learnings` são parseados do `KANBAN_RESULT` e **nunca repassados**.
  - **Caminho ATIVO confirmado:** `docker-compose.copilot.yml:32` seta `AGENT_CLI_ARGS: /app/docker/copilot-cli-adapter.mjs {prompt}` — o bridge é o caminho de produção sempre que o Copilot CLI roda (que é o default de produção, decisão 5 do dono).
  - **Impacto 1 — a colmeia nunca recebeu nada.** `orchestrator.ts:1472` (`if (runResult.learnings?.length)`) é o ÚNICO ponto onde o loop escreve memória. Com `learnings` sempre ausente, **nenhum aprendizado jamais foi gravado pelo caminho de produção**. Todo o mecanismo de memória viva (ADR-0027 / US-A4) está morto na prática — o prompt pede `learnings`, a IA emite, e o bridge joga fora.
  - **Impacto 2 — o gate de evidência estruturada é insatisfazível.** Com `AGENT_REQUIRE_STRUCTURED_EVIDENCE=true`, o gate exige `evidence` verificável para aceitar `done:true`; como `evidence` nunca chega, nenhuma task fecharia por esse caminho.
  - **Impacto 3 (o mais perigoso) — `done:true` fantasma.** Resposta só com prosa, resposta vazia, marcador órfão ou JSON inválido + exit 0 ⇒ o bridge cai no fallback **`done: true`**. Uma task pode ser dada como concluída sem NENHUM resultado estruturado.
  - **Outros 6 documentados no oráculo:** `summary` ausente vira o literal `<<<END_KANBAN_RESULT>>>`; falso-positivo de `fatalError` em prosa contendo "is not available"/"quota exceeded"; **primeiro-vence (bridge) vs último-vence (JSONL)** para blocos duplicados — critérios OPOSTOS nas duas camadas; spawn ENOENT emite result fatal duplicado e o motivo informativo é sobrescrito pelo genérico; QUESTION malformada é engolida e vira `done:true`; último rodapé de tokens malformado apaga a leitura válida anterior.
  - ⚠️ **IMPLICAÇÃO PARA O EP-F2 (importante):** o épico da colmeia pressupõe que os agents escrevem `learnings`. **Hoje esse cano está cortado no bridge.** O EP-F3 conserta por construção quando o `outputSchema` entrar (US-F3.5) — mas SÓ para os adapters que passam pelo `TanStackRunner`; o Copilot continua no bridge. Ou seja: **este bug precisa ser corrigido para o EP-F2 entregar valor com o adapter de produção.**
  - **Não corrigido de propósito:** é código pré-existente, fora do escopo do épico (regra do dono: bug de lugar paralelo é outra task). O oráculo da US-F3.2 já fixa o comportamento atual, então a correção fica verificável.

- [ ] **🔴 BUG-DI1 — `PROJECTS_ALLOW_SSH` não é aplicado e credencial HTTPS/PAT nunca resolve** *(descoberto como achado COLATERAL na US-F1.3, 2026-08-29 — pré-existente desde `c792d5c`, o commit original do EP-PROJECT)*
  - **Causa raiz:** `project-workspace.service.ts:62` declara `@Optional() private readonly credentials: ProjectCredentialsService | null = null`. O TypeScript emite **`Object`** no `design:paramtypes` para tipos UNIÃO — o Nest não resolve, e o `@Optional()` faz ele injetar `undefined` **em silêncio**. Confirmado no JS compilado: `design:paramtypes", [PrismaService, Object, RealtimeService, Object, ProjectGraphService]` — a 4ª posição (`credentials`) é `Object`. O serviço ESTÁ nos `providers` e `exports` do `projects.module.ts`; o problema é só a assinatura.
  - **Impacto 1 (segurança):** `assertSshAllowed` é a **ÚNICA** aplicação de `PROJECTS_ALLOW_SSH` (varredura confirmou: só `config.ts` lê a env e só `project-credentials.service.ts:103` a valida). Ela é chamada em `project-workspace.service.ts:140` e `:216` via `this.credentials?.` — **optional chaining sobre `undefined` ⇒ o guard nunca roda**. A flag de segurança não faz nada.
  - **Impacto 2 (funcional):** `resolveOnAuth` (linha 93) faz `if (!this.credentials) return undefined` ⇒ **clone HTTPS de repo privado nunca recebe o PAT**.
  - **Correção:** trocar por `@Optional() private readonly credentials?: ProjectCredentialsService` (sem união, sem `= null`) — exatamente o padrão que a US-F1.3 usou no parâmetro novo `graph?:` e documentou no `AGENTS.md` do módulo.
  - ⚠️ **DECISÃO DO DONO antes de corrigir — a correção MUDA COMPORTAMENTO:** com o guard funcionando, clone SSH passa a ser **rejeitado** quando `PROJECTS_ALLOW_SSH=false`, que é o **default do `docker-compose.yml`**. Quem hoje clona por SSH sem saber que a flag está off vai parar de conseguir. Ou seja: pode quebrar setup que funciona hoje justamente **por causa** do bug. Definir se corrige o código, se flipa o default da env, ou os dois.
  - **Nota:** o comentário de 2026-08-13 no backlog sobre clone ssh afirma que "o clone é REJEITADO no guard `assertSshAllowed`" — pelo que o código mostra, **esse guard não executa**; a rejeição observada na época veio de outro ponto (provavelmente a falta de chave no container). Revisar aquele diagnóstico junto com esta correção.
