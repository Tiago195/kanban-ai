- [x] **🔴 Deadlock ao FECHAR o DOD: iterações de verificação (diff vazio) puniam o `dodTouched`** — **CONCLUÍDO 2026-08-11 (build+lint+test verdes; 75/75 specs)**
  - **Causa-raiz (`orchestrator.ts`):** (1) `emptyWorktreeBypass` tratava marcar `dodTouched` como "reivindicação de código novo" e **zerava** o DOD quando o diff da iteração estava vazio — mas fechar itens de DOD de VERIFICAÇÃO (build/lint/test verde, tipo exportado) é legítimo e nunca gera diff; (2) o cap de improdutivas contava qualquer iteração `implementation` sem diff como improdutiva, sem distinguir "não escreveu o código que deveria" de "está fechando DOD de código já escrito". Combinados → deadlock de re-escalação.
  - **Correção aplicada:**
    1. **`emptyWorktreeBypass`** agora só dispara quando a task **NUNCA** produziu código (`priorProductiveDiffs === 0` **E** diff desta iteração vazio) e mesmo assim reivindica progresso. Assim: fechar DOD após o código já ter sido escrito é aceito; declarar `done` numa iteração final de fechamento é aceito; reivindicar progresso sem NUNCA ter escrito nada continua bloqueado como alucinação.
    2. **Cap de improdutivas** (`enforceLoopGuards`): iteração produtiva = tem diff **OU** fechou ≥1 item de DOD (`dodTouched`). Adicionado `dodTouched` ao select das iterações; só conta improdutiva a que NEM escreveu código NEM avançou DOD. O guard genuíno (código novo alegado sem diff) segue ativo.
  - **DOD atingido:** task cujo código foi escrito antes consegue fechar os itens restantes de DOD (incl. build/lint/test verde) e ir a `done` sem escalar por "improdutiva"; o caso genuíno ainda escala; 2 specs novos em `orchestrator-guards.spec.ts` (fechar DOD sem diff = produtivo; sem diff e sem DOD = escala); `npm run build && npm run lint && npm test` → **75/75 verde**.
  - **Evidência (TK-129):** cobaia do bug, já destravada manualmente numa etapa anterior (DOD 6/6, `execState=done`). Com esta correção, tasks futuras fecham o DOD sozinhas.
  - **Refinamento 2026-08-11 (TK-130 — mesmo sintoma, causa mais sutil):** a **TK-130** (irmã da TK-129 na mesma story US-117, mesmo repo-alvo) reincidiu no deadlock APÓS a correção acima. Motivo: seu código (`ResolveRequest`/`ResolveResponse`/`MemoryReviewItem` em `packages/shared/src/dtos.ts`) **já existia no working tree** — escrito durante a sessão da task IRMÃ (o agent roda direto no repo-alvo, sem worktree isolado; `workspace.service.ts` é stub). TK-130 destravada no banco (DOD 6/6, `execState=done`, coluna Done).
